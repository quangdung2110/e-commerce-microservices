# Review Service — Service Overview

Review Service is planned; no runtime implementation exists yet. These documents are
the target design and must be implemented together with their contracts.

## Purpose and boundary

Review grants a buyer one review entitlement per purchased SKU, maintains the public
review lifecycle, media metadata, moderation, legal takedowns and product rating
aggregates. It publishes lifecycle facts, rating snapshots and safe user-notification
requests through outbox CDC.

Review does not own orders, catalog, user accounts, object bytes, Search documents or
notifications. It receives immutable purchase snapshot fields in `ORDER_COMPLETED`
and user-deletion instructions in `USER_DELETED`; it does not call those services in
the write path.

## Data ownership

| Store | Owned data |
|---|---|
| PostgreSQL `review` | entitlement, review, media asset metadata, moderation, privacy request, aggregate, consumer receipt, export session, outbox |
| Object storage | image/video bytes |
| Kafka `t.review.events` | Review lifecycle facts, Search rating snapshots and Notification requests; transport only, not source of truth |

`variant_name_snapshot` comes from Order at completion. `author_display_name` is a
pseudonym generated by Review from trusted Gateway `user_id`; it contains neither a
profile field nor an email. Neither field is synchronized after create. Account deletion
replaces the pseudonym with `Khách hàng ẩn danh` immediately and removes direct customer
IDs at the supplied hard-delete deadline. Its retained HMAC deletion guard prevents
late/replayed input from writing that direct identity back.

## Core capabilities

- Grant and expire verified-purchase review entitlements.
- Create one review and edit it once.
- Issue bounded direct-upload URLs; verify and attach media; route detached or expired
  unattached assets through confirmed asynchronous storage cleanup.
- List only approved reviews with keyset pagination and expose rating aggregate.
- Report, auto-hide, dismiss reports, reply and legally take down reviews.
- Process all internal/inbound events idempotently with database receipts.
- Export rating aggregate through durable Search export sessions.
- Publish lifecycle facts, rating snapshots and two safe user-notification requests only through PostgreSQL outbox and Debezium.

## Critical invariants

- `REVIEW-INV-001`: one `(order_id, product_id, sku_id)` has at most one entitlement.
- `REVIEW-INV-002`: one entitlement creates at most one review.
- `REVIEW-INV-003`: review product/SKU always match its entitlement.
- `REVIEW-INV-004`: one review can be edited at most once.
- `REVIEW-INV-005`: aggregate total and average derive from star buckets.
- `REVIEW-INV-006`: every aggregate mutation increments `review_revision` and writes
  a metric outbox event in one transaction.
- `REVIEW-INV-007`: all outbound business events use outbox CDC.
- `REVIEW-INV-008`: event consumer effect is idempotent by receipt.
- `REVIEW-INV-009`: every page of an export session uses the same Kafka offsets.
- `REVIEW-INV-010`: direct customer identity is purged at `hard_delete_after`.
- `REVIEW-INV-011`: eligibility expiry derives from order completion, not ingestion.
- `REVIEW-INV-012`: a committed HMAC deletion guard blocks new direct identity writes
  for its subject, including late Order input and a notification outbox row addressed
  to that subject.
- `REVIEW-INV-013`: every detached or expired-unattached media asset enters
  `DELETE_PENDING` with a reason and becomes `DELETED` only after storage confirms
  deletion (or confirms the object is absent).

## Known gaps

- Runtime, migration tool and concrete object-storage provider are still unchosen.
  The public contract uses provider-neutral signed upload instructions; it does not
  expose object keys or a storage-vendor API.
- The privacy retention rule for admin/legal identities needs a compliance policy;
  customer erasure only covers direct customer identifiers.
- Event receipt retention must be configured to exceed Kafka retention plus replay
  safety margin before implementation is deployed.
- Order and Inventory still disagree on the value of an order identifier: Order emits
  `"10001"` while Inventory emits `"order-10001"` for the same order. Both are opaque
  strings now, so neither contract is wrong on its own, but nothing can correlate the
  two event streams until one owner adopts the other's form. Review is unaffected — it
  only consumes Order — and changing Inventory's published contract is not Review's
  call, so this is recorded rather than fixed here.
- Auth deliberately keeps best-effort `USER_DELETED` delivery with at most three
  retries and no outbox. A missed event requires Auth operational reconciliation/redrive
  before Review can start its privacy lifecycle.
